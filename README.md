# 股权投资 Agent Skills

面向股权投资机构、投资人和项目研究团队的一组 Agent Skill。它把从项目初筛、立项研究、尽调、估值、投资条款到投决会的工作拆解成可组合的 Agent 工作流，让大模型负责理解材料、整理证据、识别缺口、维护问题状态和生成决策材料。

本项目不是一套固定的关键词抽取脚本，也不是用代码替代投资人、律师、会计师或行业专家，而是为 Agent 提供一套可追溯、可复用、能持续更新的分析规范。

## 项目目标

股权投资项目通常会遇到以下问题：

- 项目材料来自 PDF、Word、Markdown、网页、邮件、会议纪要和表格，格式不统一；
- BP 中的事实、管理层主张、预测、假设和宣传性表达容易混在一起；
- 初次阅读后的问题、会议回答、新增资料和承诺如果没有写回原始状态，后续容易丢失；
- 商业、财务和法律尽调分别推进，但估值、条款和投决材料需要同一套事实基础；
- 公开搜索只能提供线索，不能自动证明公司最新工商、股权、财务、知识产权或诉讼情况；
- 无法说明数据来源、假设和证据状态的模型或报告，不适合直接作为投资结论。

本项目希望建立一个共享的投资分析工作区，使每个重要结论都能回答：

1. 这条信息来自哪里？
2. 它是材料事实、管理层主张、外部来源、推导结果还是模拟输入？
3. 它是否已经被独立验证？
4. 如果信息不成立，会影响估值、金额、持股、交易结构、保护条款还是投决结果？
5. 下一步由谁、通过什么资料或访谈来验证？

## 设计原则

### Agent 推理优先

Skill 规定 Agent 应该如何阅读材料、建立证据地图、提出判断、识别矛盾和生成输出，但不把分析简化成“出现某个词就取后面的数字”。同一个字段在不同项目、行业和阶段中的含义可能不同，Agent 必须结合上下文、单位、期间、主体和来源进行判断。

### 原始材料优先，外部搜索补充

项目 BP、公司资料包、正式合同、财务文件、会议回答和用户输入是分析的核心材料。外部搜索可以用于行业、市场、工商、知识产权、诉讼和竞争信息的线索研究，但必须记录来源、日期和限制；搜索不到不能写成“没有”。

### 事实、主张、推导和模拟严格分开

- **材料事实**：原文明确披露，并带文件名、页码、章节或其他来源定位；
- **管理层主张**：公司或项目方表达的观点、预测、客户状态、市场判断或承诺；
- **外部支持**：公开来源或用户另行提供的独立证据；
- **Agent 推导**：基于已有数据计算或逻辑推断出的结果；
- **模拟输入**：为了演示模型或测试流程而设置的代理数据，不能当成真实经营数据。

证据不足时，Skill 应输出“未知、待验证、数据不足或无法计算”，而不是补全一个看似完整的答案。

### 状态持续维护

重要问题使用稳定的 `issue_id`，并持续维护证据状态、优先级、投资影响、责任人、下一步、下游引用和变更历史。会议纪要、新增数据和承诺应写回**更新后的项目卡**、问题台账、估值输入和投资条款影响，而不是只生成一份孤立的会议摘要。

### AI 辅助判断，不替代专业责任

这些 Skill 可以帮助投资团队提取、比较、计算、追踪和起草，但不能替代：

- 律师对股权、合同、知识产权、劳动、诉讼和交易文件的法律意见；
- 会计师或审计师对财务报表、会计处理、税务和财务尽调的专业判断；
- 商业顾问、技术专家、客户访谈和现场核验；
- 投资人对估值、条款、风险承受能力和最终投决的责任。

## 完整工作流

项目可以按下列顺序推进，也可以根据项目阶段跳过不适用环节。跨环节时应尽量携带结构化工作区和稳定问题 ID。

```text
项目材料
   ↓
项目卡 + 首轮问题清单 + 访谈提纲
   ↓
会议纪要 / 新增数据 / 回答 / 承诺 / 矛盾
   ↓
更新后的项目卡 + 问题状态更新
   ↓
立项研究 + 资料需求清单
   ↓
尽调启动判断 + 统一尽调工作区
   ├─ 商业尽调
   ├─ 财务尽调
   └─ 法律尽调
   ↓
财务预测与估值 + 退出收益
   ↓
投资条款分析
   ↓
投决会报告
```

实际项目通常会在研究、资料补充、访谈和尽调之间多轮循环。每一轮都应保留上一轮结论，注明发生了什么变化，并说明变化是否影响估值、条款或投决建议。

## Skill 清单

当前仓库包含 11 个 Skill。每个 Skill 都可以单独调用，也可以通过统一尽调工作区连接起来。

| Skill | 目录 | 主要作用 | 核心输出 |
| --- | --- | --- | --- |
| 项目初审 | `project-intake-and-project-card` | 读取 PDF、Word、Markdown、纯文本或混合材料，建立统一证据地图 | 项目卡、首轮问题清单、首次访谈提纲 |
| 会后更新 | `update-project-card-from-meeting` | 将会议回答、新增资料、承诺和矛盾写回原始项目状态 | **更新后的项目卡**、问题状态更新、变更摘要、未闭环事项 |
| 立项研究 | `project-initiation-research-and-memo` | 根据项目阶段确定研究问题，结合来源开展迭代研究并管理资料缺口 | 当前立项研究报告、研究摘要、资料需求清单 |
| 尽调启动 | `due-diligence-intake-and-request-list` | 根据项目阶段、交易结构和已知风险制定定制化尽调范围 | 尽调启动判断、资料清单、验证任务和优先级 |
| 统一工作区 | `due-diligence-workspace-and-issue-ledger` | 维护跨商业、财务、法律尽调的问题、证据、影响和变更记录 | 统一尽调工作区摘要、问题台账、证据和下游输入 |
| 商业尽调 | `commercial-due-diligence-analysis` | 分析市场、客户、竞争、商业模式、订单转化、单位经济和扩张假设 | 商业尽调分析报告、商业问题与投资影响 |
| 财务尽调 | `financial-due-diligence-analysis` | 分析财务报表、总账、现金流、营运资本、异常和盈利质量 | 财务尽调分析报告、指标、异常、调整和资料请求 |
| 法律尽调 | `legal-due-diligence-analysis` | 从投资人角度梳理股权、工商、控制权、IP、劳动、诉讼和交易风险 | 法律尽调分析报告、法律问题、保护措施和律师复核事项 |
| 财务预测与估值 | `financial-forecast-and-valuation` | 把证据、尽调结论和明确假设转成预测、估值、持股和退出收益模型 | 财务模型、估值区间、持股分析、情景与回报摘要 |
| 投资条款 | `investment-terms-analysis` | 将尽调风险、估值不确定性和交易目标映射到投资人保护条款 | 投资条款工作包、谈判问题、交割条件和保护措施 |
| 投决会 | `investment-committee-decision-memo` | 汇总立项、尽调、估值、回报、条款和未解决风险 | 投决会结论摘要、决策材料、条件和待决事项 |

### 三个尽调 Skill 的分工

- **商业尽调**：验证客户是否真实、需求是否可持续、订单能否转化、市场口径是否一致、竞争壁垒是否成立、扩产是否可交付；
- **财务尽调**：检查收入质量、毛利、费用、现金、营运资本、债务、资本开支、关联交易、一次性项目和财务数据之间的勾稽关系；
- **法律尽调**：检查股权沿革、实际控制、代持和质押、工商变更、核心 IP 权属、核心人员安排、合同、劳动与工伤、诉讼、处罚和交易可执行性。

三者都应维护问题对投资决策的影响，例如是否需要降低估值、分期投资、里程碑付款、资金用途监管、交割前解决、陈述保证、赔偿、保留事项、信息权、投后监控，或暂停、附条件推进和终止项目。

## 输入与输出约定

### 支持的输入材料

根据具体 Skill，可以提供：

- PDF、DOCX、Markdown、纯文本和网页链接；
- BP、公司介绍、产品资料、市场材料、客户及订单资料；
- 财务报表、科目余额表、总账、银行流水、税务资料、预算、预测和 Excel 数据；
- 股东名册、章程、工商档案、股权转让文件、借款协议、合同、专利和软件资料；
- 会议纪要、访谈记录、邮件跟进、管理层回答、新增数据和承诺；
- 用户已经搜索或整理好的外部信息，以及需要 Agent 继续研究的资料需求清单。

### 共同输出要求

每份报告至少说明：

1. 分析范围、主体、期间、数据截止日和使用的材料；
2. 当前证据基础及其质量；
3. 已确认事实、管理层主张、推导结果和模拟输入；
4. 重要矛盾、证据缺口和不确定性；
5. 对估值、投资金额、条款和投决的影响；
6. 下一步需要谁补充什么、通过什么方式核验；
7. AI 分析的边界，以及需要投资人或专业人士复核的部分。

Markdown 报告与 JSON、Excel 或其他结构化输出必须保持一致：项目名称、期间、数值、问题 ID、状态、优先级、来源和结论不能互相冲突。

## 中文输出规范

所有面向用户的分析、报告、项目卡、问题清单、访谈提纲、台账说明、表格标题、结论、建议和警示，默认使用简体中文。

以下内容可以保留英文或原文：

- 公司、人名、机构名、产品名和官方名称；
- 文件名、URL、代码、公式、JSON/YAML 键和稳定 ID；
- 必要的专业缩写，例如 DCF、EBITDA、IRR、MOIC；
- 原始合同、判决、工商记录、会议原话和外部来源的直接引用。

必要的英文专业缩写首次出现时应附中文释义。机器状态或结构化枚举可以保留英文，但如果 JSON 或表格直接给用户阅读，必须同时提供中文显示值或说明。Agent 自己的分析和结论不得因为原始材料是英文而改用英文输出。

## 证据与状态管理

统一尽调工作区建议至少维护以下字段：

- `issue_id`：稳定的问题编号，例如 `COM-001`、`FIN-001`、`LEG-001`；
- 来源引用：文件、页码、章节、链接、日期或材料版本；
- 证据状态：已确认、管理层主张、待验证、存在冲突、资料缺失、无法计算等；
- 优先级：通常使用 P0、P1、P2，必要时说明停止条件；
- 投资影响：对估值、金额、持股、交易结构、交割、保护条款和投决的影响；
- 下游输入：该问题会影响哪个模型、报告、条款或投决结论；
- 责任人与下一步：项目方、投资人、律师、会计师、技术专家或其他负责人；
- 变更历史：什么时候新增、回答、修正、降级或重新打开。

问题已经“得到回答”不等于已经“得到验证”。管理层口头回答、承诺提供材料和实际收到的文件也必须分开记录。

## 隐私与公开仓库边界

本项目默认只把通用 Skill、规范、模板和合成案例放入 GitHub。真实项目材料和测试输出可能包含商业秘密、未公开财务数据、客户信息或交易信息，不应上传到公开仓库。

当前 `.gitignore` 已忽略：

- `outputs/`：生成的项目卡、立项报告、尽调报告、Excel 模型和测试结果；
- 根目录下的 `*.pdf`：BP 和其他 PDF 原始材料；
- `ChatGPT-*.md`：项目讨论记录和对话导出文件；
- 本地工具和操作系统生成的临时文件。

提交前应检查：

```bash
git status --short
git check-ignore -v <疑似敏感文件>
git diff --cached --name-only
```

不要使用 `git add -f` 强行加入 BP、会议纪要、真实项目输出或其他保密文件。即使文件被 `.gitignore` 忽略，也应在提交前重新检查工作区是否存在敏感信息。

## 安装与调用

### 获取仓库

```bash
git clone https://github.com/MXmingxuan/MXmingxuan-equity-investment-skills.git
cd MXmingxuan-equity-investment-skills
```

### Skill 目录结构

每个 Skill 都是一个独立目录，至少包含：

```text
skills/<skill-name>/
├── SKILL.md                 # Agent 的主要工作规范
├── agents/openai.yaml       # 展示信息与默认调用提示
└── references/              # 结构化输出契约、模板或合成测试材料
```

在支持 Agent Skill 的宿主中，将需要使用的目录安装或导入到宿主的 Skill 目录即可。可以只安装单个 Skill，也可以安装整套 Skill；如果要做连续投资流程，建议同时安装统一尽调工作区和所需的业务 Skill。

### 推荐调用方式

初次拿到 BP 时：

```text
请使用 project-intake-and-project-card 阅读我提供的项目材料，生成项目卡、优先级问题清单和首次访谈提纲。
```

拿到会议纪要后：

```text
请使用 update-project-card-from-meeting，根据原项目卡、原问题清单和本次会议纪要，输出更新后的项目卡，并维护问题状态、变更摘要和未闭环事项。
```

进入立项研究后：

```text
请使用 project-initiation-research-and-memo，根据当前项目卡和已有资料，先确定研究问题，再使用可追溯来源开展研究；无法确认的内容列入资料需求清单。
```

进入正式尽调后，建议先调用 `due-diligence-intake-and-request-list`，再初始化 `due-diligence-workspace-and-issue-ledger`，然后按项目需要调用商业、财务和法律尽调 Skill。估值、条款和投决 Skill 应引用尽调台账中的问题 ID 和证据状态。

## 开发与验证

Skill 修改后应检查：

1. `SKILL.md` 的 front matter 中 `name` 和 `description` 是否有效；
2. 默认调用提示是否清楚、是否包含中文输出要求；
3. 输入、边界、证据规则和 Required output 是否一致；
4. 引用的文件和相对路径是否存在；
5. Markdown 与结构化输出是否使用同一套字段、状态和问题 ID；
6. 是否把模拟数据、管理层主张或搜索线索误写成已验证事实；
7. 是否意外包含真实项目名称、BP、会议记录或其他敏感信息。

如果宿主提供 `quick_validate.py`，可以对单个 Skill 或全部 Skill 运行验证：

```bash
python /path/to/quick_validate.py skills/<skill-name>

for skill in skills/*; do
  if [ -f "$skill/SKILL.md" ]; then
    python /path/to/quick_validate.py "$skill"
  fi
done
```

本仓库当前已通过全部 11 个 Skill 的结构校验。真实项目测试材料仍保存在本地忽略目录中，不作为公开示例提交。
